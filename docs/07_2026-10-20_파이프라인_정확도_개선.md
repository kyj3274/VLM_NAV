# 07. 파이프라인 정확도 개선 — 실험 A~E와 최종 결과 (2026-10-20)

> 한 줄 요약: **YOLOE + OCR(2048) + "첫 자리 다수결" 호실 규칙 + VLM은 '고르기'만** 하는 구조로, 평가용(test) 117장에서 호실 F1 **86 → 89**, 틀린 호실 **19 → 10**, 가까운 호실 **23/23(100%)**, 시간 중앙값 **3.9초**. VLM 단독(qwen3-vl 4B) 대비 호실 F1 **32 → 89**.

---

## 1. 목표와 조건
- 시각장애인 실내 길안내용으로 사진 1장에서 이동 단서(`rooms, floors, spaces, landmarks, directions`)를 뽑는다.
- **정확도 최우선**, 단 서버에서 사진 1장 처리 시간 **중앙값 ≤ 5초**.
- 특히 **가까운 호실을 정확히** 읽는 것이 중요하다(먼 번호를 많이 읽는 것보다).
- 제로샷 지향: 계단·화장실 보완, YOLOE 영어 표현 재조정, 우리 건물 전용 규칙은 하지 않는다. 프롬프트에 구체적 숫자 예시를 넣지 않는다.
- 주요 지표 순서: (1) 가까운 호실 재현율 + 호실 정밀도 → (2) 호실 F1 → (3) 랜드마크 5종 F1 → (4) 시간.

## 2. 채점 기준 v2 (`review/survey_v2.json`)
- **사람 정답이 아니다.** 사진 조사(v1) + 1단계 OCR이 찾은 호실 후보를 잘라 에이전트가 확인한 **참고 기준**이다.
- **가까운 호실** = 문패 숫자 글자 높이 ≥ 사진 높이의 **1.5%**.
- 분할: dev 59장(설정 고르기용), test 117장(마지막에 한 번만 채점). 3층 중복 50장은 뺐다(176장).
- 호실 정답 111개(dev 38 / test 73), 그중 가까움 29개(dev 6 / test 23). 읽을 수 없는 문패 2개는 채점 제외.
- 한계: 호실 후보를 m2048 OCR 결과에서만 만들었기 때문에 **OCR 방식에 유리**하다. OCR이 못 찾은 문패는 정답에도 없다. 그래서 실험 A에서 dev의 새 후보 41곳을 눈으로 확인해 실제 문패 7개를 더한 **보정 기준**(`outputs/kyj/exp_a_extra_rooms.json`, `score_v2_adj.py`)도 함께 봤다.
- 채점: `python3 src/score_v2.py --split {dev,test,all} 이름=결과.jsonl ...`

## 4. 최종 설정 — `src/pipeline_final.py`

```
사진 ─┬─ YOLOE (yoloe-11l-seg, 1280, 3A 평균 표현, conf 0.15)        GPU 3
      └─ PaddleOCR (PP-OCRv5_mobile_det + korean_mobile_rec, 긴 변 2048)  GPU 3
           │
           ▼ 합치기(pipeline.combine) + 호실 규칙(room_rules.BEST = 첫 자리 다수결, 점수 ≥ 0.5, 큰 글자 순)
           │
           ├─ 애매한 것이 없으면 → 끝 (0.2~1초)
           └─ 있으면 VLM 한 번 (qwen3-vl:4b-instruct, Ollama 11436, GPU 7, JSON schema로 답 제한)
                R: 애매 호실 후보(점수 0.5~0.9 / 다수결로만 버린 큰 글자 / 점수 0.3~0.5 큰 글자) → 예/아니요/판단 불가
                E: YOLOE 엘리베이터 상자 conf ≥ 0.15 인데 1단계가 확정 못함 → 예/아니요/판단 불가
                S: 비상구표시 conf ≥ 0.15 → 화살표 방향(시계 방향, 최대 2개)
```

- 반영: 점수 낮은 출력 후보가 '아니요'면 뺌, 버린 후보가 '예'면 넣음, 엘리베이터 '예'면 추가, 화살표는 `SIGN_ARROW`. 판단 불가·오류면 1단계 결과 유지.
- 실행 (서버):
  ```
  cd /workspace/capstone/src/kyj
  ./gpu_lock.sh 3 ./gpu_lock.sh 7 env CUDA_VISIBLE_DEVICES=3 .venv/bin/python pipeline_final.py --name final_all
  ```
  → `outputs/kyj/exp_final_all.jsonl` (옵션: `--ids-file`, `--limit`, `--model`, `--url`)
- 시간 기록: `latency_seconds` = YOLOE + OCR + 규칙 + VLM(축소·자르기·인코딩·요청). JPEG 디코딩은 기존 실험과 같이 빼고 `decode_seconds`, `latency_with_decode_seconds`에 따로 남겼다(디코딩 포함 중앙값 3.88초). 모델 로드·예열은 제외.

## 6. VLM 단독 대비 개선점
- **호실**: qwen3-vl 단독은 test 호실 73개 중 14개만 읽었다(F1 32). 최종은 67개(F1 89). 가까운 호실은 48% → **100%**.
- **호실 정밀도**: VLM 단독(qwen2.5vl)은 틀림 14개, 이전 OCR 1단계는 19개, 최종은 **10개**(다수결 규칙 + VLM 확인).
- **화살표**: VLM 단독은 화살표를 거의 못 맞히고 오탐이 많다(qwen2.5vl 오탐 50장). 최종은 2/3장 찾고 방향 2/2, **오탐 0**.
- **시간**: qwen2.5vl 단독(8.5초)과 달리 조건 안(3.9초). VLM은 애매한 사진에만 한 번, 짧은 객관식으로 부른다.
- 문·비상구표시는 VLM 단독 이상, 층 표시는 비슷하다.

## 7. 한계 (test에서 드러난 것 포함)
- **엘리베이터 판단이 test에서 무너졌다.** dev는 P 100이었는데 test는 P 18이다. VLM이 일반 문·금속 문에 '예'라고 답한 사진이 12장이다(4F_003, 4F_018, 4F_021, 4F_024, 4F_026, 4F_066 등). dev 엘리베이터 정답이 8장뿐이라 dev 결과가 우연에 가까웠다. 엘리베이터는 VLM 단독(R 100)이 오히려 재현율이 높다.
- **계단 0, 화장실 30**: YOLOE 표현 재조정·건물 특화 규칙을 하지 않기로 해서 그대로 두었다. VLM 단독(qwen3-vl)이 화장실 F1 60으로 더 낫다.
- **VLM 확인이 먼 정답을 버리기도 한다**: test에서 516(5F_002), 503(5F_033)에 '아니요'라고 답해 맞은 호실 2개를 잃었다. 반대로 195·246·104에는 '예'라고 답해 틀린 호실을 남겼다. qwen3-vl은 '판단 불가'를 거의 쓰지 않는다.
- **2xx 오독 묶음**: 4F_048, 4F_059에서 다수결이 오독끼리 다수가 되어(250·254·251·246, 195·193·199) 틀린 호실을 남겼다. 다수결은 "한 사진의 진짜 호실이 다수"라는 가정에 기대고 있다.
- **시간 꼬리**: 중앙값은 조건 안이지만 5층(5712×4284) 사진은 중앙 4.36초이고, 176장 중 23장(13%)이 5초를 넘는다(최대 7.56초, 5F_033: 1단계 2.5초 + VLM 5.0초). 디코딩을 포함하면 0.06초 더 걸린다.
- **VLM 오류 1건**: 3F_002는 YOLOE 엘리베이터 상자가 사진 왼쪽 끝 얇은 띠(가로 2%)라서 잘라낸 조각이 아주 가늘어지고, Ollama가 500 오류를 낸다. 1단계 결과로 대신했다(실험 D에서도 같았음).
- 기준 v2가 사람 정답이 아니고 OCR 쪽에 유리하다. dev 가까운 호실은 6개뿐이다.
- 다른 팀원(lsh)이 같은 Ollama(11436)를 동시에 쓰면 시간이 늘 수 있다(이번 실행의 VLM 호출 시간은 실험 D와 거의 같았다. 예: 3F_044 4.08초 vs 4.12초).

## 8. 다음 할 일
1. **엘리베이터 질문 개선/재검증**: 엘리베이터 정답이 더 많은 사진으로 검증 세트를 늘린 뒤 E 질문을 다시 본다(예: E 상자 conf 기준 상향, 호출 버튼·층 표시를 따로 묻는 질문). dev 8장으로는 판단할 수 없다.
2. **너무 가는 조각 막기**: 조각의 짧은 변이 일정 픽셀(예: 32px) 미만이면 넓혀서 보내도록 고친다(3F_002 오류). 동작 변경이므로 새 dev/test 분할에서 다시 채점한다.
3. **시간 꼬리 줄이기**: 5층 큰 사진은 디코딩·축소 비용이 크다. JPEG draft 모드로 줄여 읽기, VLM 조각 수 제한(E·S 최대 3장) 등을 검토한다.
4. **사람 정답 만들기**: 아래 "직접 확인할 것"을 먼저 확인하고, test 가까운 호실 23개 정도는 사람이 확인해 기준을 확정한다.
5. 계단·화장실은 이번 범위(제로샷, 건물 특화 금지) 밖이다. 필요하면 별도 실험으로 VLM 단독의 화장실 판단을 가져오는 방안을 본다.
