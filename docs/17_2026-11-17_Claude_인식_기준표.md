# 17. Claude 인식으로 바꾼 기준표 (2026-11-17, 브랜치 claude)

VLM_NAV의 규칙 흐름(`Navigator.step`)은 그대로 두고, 인식(YOLOE·PaddleOCR·Places365·Ollama)을 **Claude Haiku 5.5 호출**(충남대 게이트웨이)로 바꿨다. 다른 AI 모델은 쓰지 않는다. 예전 인식 코드는 `src/nav/legacy/`에 옮겨 두었다(실행에는 쓰지 않음).

## 1. 인식: 무엇을 Claude에게 묻나

1초 구간(8장)에서 가장 선명한 장 1장을 보낸다(VLM_NAV `--key sharp`와 같음). 출력은 짧은 영문 키(출력 토큰을 줄여 시간을 줄이려고).

| 칸 | 내용 | VLM_NAV에서 하던 것 |
|---|---|---|
| `plates[]` | 문패: `n` 번호, `name` 방 이름, `side` L/C/R(화면 가로 1/3), `m` 거리, `on` door/wall/board, `box` 위치(0~100) | OCR 글자 + `room_rules` 호실 판정 + YOLOE 문 상자 |
| `floor_sign` | 층 표지 글자(엘리베이터 운행 표시는 제외) | OCR 층 글자 |
| `place` | corridor, lobby, elev_hall, entrance, junction, room_door, in_elev, stairs, unknown | Places365 묶음 + VLM scene_type |
| `door_ahead` | 지나가야 할 출입문 glass/door/none | VLM context `door_ahead` |
| `elev` | `seen`, 근거 `why`(button 호출 버튼 / display 층 표시창), `side`, `m`, `btn`(호출 버튼이 문 왼쪽/오른쪽) | Places365 elevator/door ≥ 0.5 |
| `arrows[]` | 화살표 표지 `to` L/R/F/B, `label` | OCR 방향 글자 |
| `say` | 짧은 한 문장(보조) | VLM은 문장을 쓰지 않았음 |

- 번호가 안 읽히고 방 이름만 읽힌 문패는 `unread`로 따로 두고, 확대 재확인으로 번호를 읽는다(VLM_NAV의 "문패 한글만" 애매함 처리 대신).
- `side`는 모델 값 대신 `box` 가운데 위치로 다시 정한다(첫 측정에서 상자는 오른쪽인데 side가 C로 온 경우가 있었음).
- 엘리베이터 `seen`인데 근거가 `none`이면 안 본 것으로 고친다.
- 목적지가 호실이면 인식 요청에 목적지를 넣지 않는다 → 같은 프레임 결과를 경로·목적지가 달라도 다시 쓴다(캐시, 규칙만 바꾼 재생은 크레딧 0). 호실이 아닌 목적지(화장실 등)는 `dest` 칸을 더한다.

**확대 재확인(recheck):** 한 초에 최대 1개. 원본 해상도에서 `box` 주변을 잘라(작으면 긴 변 512로 키워) 번호만 다시 읽는다. 대상 우선순위: ① 목적지 ±2 번호 ② 이름만 읽힌 문패(층 모름이거나 목적지 층일 때) ③ 층을 처음 정할 번호 ④ 층 충돌 번호. 8장 OCR 투표 대신 쓴다.

## 3. Claude `say` 검사 (규칙 상태와 안 맞으면 쓰지 않고 `say_check`에 이유만 기록)

- "엘리베이터"를 말했는데 확인된 엘리베이터가 없음
- "○층"이 확인된 층과 다름(층 모르면 모두 거부)
- 세 자리 이상 번호가 확정 문패가 아님
- "목적지"·목적지 이름을 말했는데 목적지를 아직 못 봄
- "왼쪽/오른쪽으로 가라" 지시에 같은 방향 화살표가 이번 사진에 없음, "뒤로/돌아" 지시
- "직진" 지시가 지금 규칙 행동(뒤로 돌기, 엘리베이터 등)과 다름

## 7. 목적지 확정 안전장치 (2026-11-18, 사용자 지시)

- 층 판단과 일반 문패: 그대로 (확대 재확인 일치·또렷한 층 표시는 한 번의 호출로 확정).
- **목적지 번호(또는 목적지 이름)**: 믿음 점수 3과 함께 **서로 다른 호출(다른 걸음의 사진) 2번**에서 읽혀야 확정.
  같은 사진을 잘라 본 확대 재확인은 두 번째 호출로 치지 않는다. 그 전에는 "목적지 같습니다, 확인 중입니다."까지만 말하고
  (행동 = 목적지 접근), 확정 전의 목적지 문패는 층 판단·진행 방향에도 쓰지 않는다. `nav_memory.TARGET_CALLS = 2`.
- **415 오독 원인** (3단계 겹쳐 보내기, 4층 30.0초, 프레임 i0229, 실제는 413 "컴퓨터실습실1"):
  1. 인식 호출은 번호를 못 읽고 이름만 읽음 (`n=""`, 이름 "컴퓨터실습실1", 상자 [57,26,64,31], 3m, 벽).
  2. 그래서 "번호 안 읽힌 문패"로 확대 재확인 대상이 됨. 잘라 낸 위치는 맞았다(문패가 조각 가운데. 확인 그림: outputs/eval/415_i0229_crop.jpg, _full.jpg).
     조각 속 번호는 작고 흐려서 413/415 구분이 어렵다. 재확인 호출이 "415"라고 읽음.
  3. 재확인이 "일치"한 것이 아니다. 첫 호출에 번호가 없었으므로 재확인 번호가 그 걸음의 **유일한 읽기**(1점)였고,
     정면 가까이(가운데, 3m) 1점 + 확정한 412와 10 이내 1점 = 3점으로 한 번에 확정됐다
     (기억 기록: "415호 문패 확정 (C, 1번 읽음, 정면 가까이, 본 번호와 가까움)").
  4. 이번 안전장치는 415가 목적지가 아니라서 이 경우 자체는 막지 않는다. 같은 일이 목적지 번호에서 일어나면
     (예: 413을 410으로 읽음) 다음 호출에서 다시 읽힐 때까지 확정하지 않는다. 일반 문패 규칙은 지시대로 그대로 둠.
