# 19. 장면 그래프와 깊이 모델 적용 결과 (2026-11-17)

> 11/24 코드 정리 뒤 위치: 로컬 버전은 `src/nav/local/`, 깊이는 `src/nav/core/depth.py`. 이 문서의 `src/nav/...` 경로는 정리 전 기준이다.

## 한 줄 요약

**새 코드는 예전 규칙이 틀리던 "반대 방향" 상황을 맞히고, 맞던 상황은 그대로 맞힌다.**

## 바꾼 것

| | 예전 | 지금 |
|---|---|---|
| 방향 판단 | 읽은 번호를 한 줄로 놓고 목적지와 차이가 줄었는지 비교 | 확실한 문패만 벽별로 지나간 순서대로 놓은 그래프에서, 번호 흐름(앞으로 갈수록 커지나/작아지나)으로 목적지가 앞인지 뒤인지 판단 |
| 벽 판단 | 화면 왼쪽/오른쪽 | 깊이 지도에서 복도가 뻗는 쪽(가장 먼 열) 기준 |
| 그래프 기준점 | 읽힌 번호 전부 | 확정됐고, 벽이 일관되고(2/3 이상), 7m 안까지 가까이 지나간 문패만 |
| 목적지 거리 | 문 높이(2.1m 가정)로만 | 문 높이와 깊이 중 짧은 쪽 |

새 안내 문장
- "316호를 지났습니다. 314호는 앞쪽입니다. 계속 직진하세요."
- "318호는 뒤쪽인 것 같습니다. 뒤로 돌아 주세요." (돌아선 뒤에는 앞의 순서를 버리고 새로 본 문패로 다시 판단)
- "314호 근처입니다. 문패를 확인하며 천천히 가세요." (목적지와 번호가 바로 옆일 때)

코드: `src/nav/depth.py`(새 파일), `src/nav/nav_memory.py`(`direction`), `src/nav/navigator.py`(`direction_say`, 깊이 반영), 그래프 초안 `src/eval/scene_graph.py`

## 결과

### 좋아진 것

- **반대로 걸을 때**: 318호인데 반대로 가는 상황에서 예전 규칙은 "방향이 맞습니다"라고 틀렸다. 새 코드는 문패 2개(317, 316)를 지난 8초에 "318호는 뒤쪽인 것 같습니다. 뒤로 돌아 주세요"라고 맞혔다. 영상과 11/16 휴대폰 시연 기록 모두 같다.
- **맞게 걸을 때**: 314호로 가는 길에서 8초에 "앞쪽입니다", 14초에 "근처입니다"로 안내했다.
- **판단 지점 점수** (엘리베이터에서 내린 뒤 13개): 예전 규칙 11개, 새 방식 12개.
- **벽 구분**: 깊이 모델로 3층 문패 21번의 벽을 모두 맞혔다. 화면 위치로는 14번.

### 그대로인 것

- 4층 410호 안내(엘리베이터 → 4층 확인 → 도착)는 예전과 같다. 시험 중 깊이 거리만 믿어 도착을 놓친 문제가 있어 두 거리 중 짧은 쪽을 쓰게 고쳤다.
- 속도는 거의 같다. 1초 처리 중앙값 0.37초, 깊이 모델은 장당 0.13초(서버 P100, 메모리 0.3GB).

### 시험 중 고친 오류

1. 사진 4장을 다시 볼 때 다른 장에서 읽힌 문패(310, 300)에 대표 사진의 깊이 지도를 써서 벽이 틀렸다 → 깊이로 벽을 정하는 건 대표 사진에서 읽힌 문패만.
2. 멀리서 읽힌 번호 때문에 순서가 꼬였다 → 7m 안까지 지나간 문패만 기준점, 순서는 가장 가까이 지난 때로.
3. 깊이 거리가 문 높이 거리보다 길게 나와 도착을 놓쳤다 → 둘 중 짧은 쪽.

### 아직 모르는 것

- **뒤로 돈 다음**: "뒤로 돌아 주세요" 뒤에 실제로 돌았을 때 "앞쪽입니다"로 바뀌는지는 기록이 없어 확인하지 못했다. 휴대폰 시연 필요.
- **다른 건물**: 같은 건물 기록으로 만들고 같은 기록으로 시험해서 실제보다 좋게 나왔을 수 있다. 특히 "목적지와 차이 1이면 방향을 단정하지 않음"은 이 복도(315 → 313 → 314 순서)를 보고 정했다.
