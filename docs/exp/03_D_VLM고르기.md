# 03. 실험 D — VLM은 '만들기'가 아니라 '고르기'만 (2026-10-20)

## 무엇을 했나
- 1단계: 실험 A `exp_a_m2048` 원자료와 B1 규칙(`room_rules`, 첫 자리 다수결)을 썼다. 1단계 시간은 실험 A에서 서버로 잰 YOLOE+OCR 값을 그대로 쓴다.
- 2단계: VLM은 `qwen3-vl:4b-instruct`(Ollama 11436, GPU 7, `gpu_lock.sh 7`)이다. 아래 조건 중 하나라도 맞는 사진만 **한 번** 부르고, 그 사진에 필요한 질문만 묶어서 묻는다.
  - R: 애매 호실 후보(`room_rules.ambiguous_reason`: kept_low / maj_big / weak_big), 최대 3개
  - E: YOLOE '엘리베이터' 상자 conf ≥ 0.15이고 1단계가 엘리베이터를 확정하지 못한 경우. NMS를 거친 상위 2개
  - S: YOLOE '비상구표시' conf ≥ 0.15(화살표 가능), 상위 2개
- 답 형식은 schema로 제한했다. `R1..`과 `E1..`은 "예/아니요/판단 불가" 중 하나이고, `arrows`는 시계 방향 enum 배열(maxItems 2)이다. num_predict는 96, temperature는 0, seed는 42다. 프롬프트에는 건물 특화 설명이나 숫자 예시를 넣지 않았다.
- 반영 규칙
  - kept_low 후보: '아니요'면 뺀다.
  - maj_big/weak_big 후보: '예'면 넣는다.
  - E: '예'면 엘리베이터와 그 위치(시계 방향)를 넣는다.
  - arrows: SIGN_ARROW로 넣는다.
  - '판단 불가'나 오류면 1단계 규칙 결과를 따른다.
- 변형
  - D1: 전체 사진(1024px) + 후보 번호·위치를 텍스트로 준다.
  - D2: D1 + 사진 위에 후보 상자와 번호를 그린다(Set-of-Mark).
  - D3: D1 + 원본에서 자른 후보 조각(호실 384px, 엘리베이터 512px, 표지 384px)을 함께 보낸다.
  - D3c: 조각만 보낸다.
  - D3h: 호실 질문만 있는 사진은 조각만, 엘리베이터·화살표 질문이 있으면 전체 사진 + 조각을 보낸다.
  - 참고로 D3을 qwen2.5vl:7b로도 돌렸다.
- 시간은 사진 1장 기준 1단계(YOLOE+OCR)에 VLM(이미지 줄이기·자르기·인코딩·요청)을 더한 값이다. 1단계처럼 원본 디코딩 시간은 빼고 `decode_seconds`에 따로 기록했다. 모델을 올리는 첫 호출은 시간에서 뺐다.
- 스크립트
  - `src/kyj/exp_d_vlm.py`(서버 같은 경로)
  - `src/kyj/exp_d_analyze.py`: 채점과 호출 통계. `--subset el,ex,rooms`는 더 좁은 호출 조건을 근사로 시뮬레이션한다.
  - `src/kyj/exp_d_diag_score.py`: 호실 확인 진단

## 결론
- **선택: D3h**(qwen3-vl 4B, E·S 0.15)
  - 가까운 호실 6/6, 호실 정밀도는 B1과 같다.
  - 엘리베이터 F1이 22에서 77로, 화살표가 0/2에서 2/2(오탐 0)로 올랐다.
  - 시간 중앙값은 3.43초(≤ 5초)다.
- D1·D2가 dev 호실에서 1개 더 낫다(597 제거). 하지만 진단표를 보면 D1·D2는 1024px 전체 사진에서 먼 문패를 거의 읽지 못한다. 먼 정답 문패 26개 중 16~18개에 '아니요'라고 답했고, D2는 가까운 정답 3/6까지 '아니요'라고 했다. 즉 597을 맞힌 것은 기본적으로 '아니요'로 답하는 경향 덕분이다. test에는 애매 사진이 16장이라 D1·D2를 쓰면 맞는 kept_low 후보를 잘못 뺄 위험이 크다. 실제로 597은 원본 조각에서도 사람 눈에도 597로 보일 만큼 흐리다.
- 조각(crop)은 호실 확인에 결정적이다. D3c가 먼 정답 23/26, 오답 5/6으로 가장 정확하다. 반면 엘리베이터는 전체 사진 맥락이 필요해서 조각만 주면 재현율이 62%에서 38%로 떨어진다. 그래서 질문 종류에 따라 이미지를 나누는 D3h로 정했다. dev 답은 D3와 같고 조금 빠르다.
- '판단 불가'는 qwen3-vl에서 한 번도 나오지 않았다(0/37). qwen2.5vl:7b는 판단 불가를 자주 쓰지만, 호출당 5.6초여서 시간 예산을 넘는다.
- 계단·화장실·비상구표시(탐지)는 VLM 질문 대상이 아니어서 변하지 않았다.
- 호출 비율이 68%로 높은 것은 거의 엘리베이터 후보 때문이다(32/40). 시간 예산이 빠듯해지면 S 기준을 0.4로 올리는 것이 dev에서 손해가 가장 적다(화살표 1개만 잃음, 중앙 2.17초). 다만 dev 화살표 정답이 2장뿐이라 기본값 0.15를 유지했다.
- 주의할 점
  - dev 차이는 대부분 사진 1~2장이다.
  - D3h에서 E 질문 32개 중 '예'는 4개이고 모두 진짜 엘리베이터다(D1은 5개 중 1개 오답).
  - 1단계 시간은 실험 A에서 잰 값을 재사용했다.
  - lsh가 같은 Ollama를 쓰면 시간이 흔들릴 수 있다.
