팀 초안(v1)을 바탕으로, signs 실험(10/4)에서 실제로 겪은 문제를 반영해 빈 곳을 채운 안.

## 2. Ground Truth 작성 규칙

### 2-1. 공통 원칙
1. **사진에서 보이는 것만** 기록한다. 파일명·촬영 위치로 아는 정보는 넣지 않는다.
2. **어디까지 기록하나**: 길안내에 쓰이는 표지판·문패·안내판·시설만. 포스터·공지문·광고 속 글자는 제외 (10/17 결정).
3. 읽기 애매한 글자는 `uncertain`에 넣는다 → 모델이 맞혀도 틀려도 점수에 반영 안 함.
4. 같은 값이 여러 번 보여도 한 번만 쓴다.

### 2-2. 필드별 규칙

| 필드 | 넣는 것 | 넣지 않는 것 | 형식 |
|---|---|---|---|
| `rooms` | 문패·표지판의 호실 번호 | 전화번호, 날짜, 포스터 속 숫자, 층수 | "호" 제거, 숫자·하이픈·알파벳 그대로: `"310-1"`, `"B101"` |
| `floors` | 글자로 적힌 층 표시 (층 안내판, 엘리베이터 표시, `3F` 표지) | 파일명으로 아는 층, 호실 번호에서 유추한 층 | `"3층"`→`"3F"`, 지하 `"B1"` |
| `spaces` | 글자로 적힌 공간·시설 **이름** | 글자 없이 눈으로만 보이는 시설 | 보이는 글자 그대로: `"창의SW설계실"`, `"강의실 1"` |
| `landmarks` | 사진에 **실제로 보이는** 이동 기준 시설·물체 | 글자로만 언급된 것 (예: 안내판에 "엘리베이터 →"만 있음) | 아래 고정 목록의 이름만 |
| `directions` | 화살표가 가리키는 방향, 랜드마크의 화면 속 위치 | 추측한 방향 | 2-3 참고 |

**landmarks 고정 목록 (23개, 10/17 사진 176장 조사 반영)**

괄호 안은 176장 중 보인 사진 수(대략). 기본 = 데이터에 적게 나와도 길안내에 꼭 필요해서 넣은 것.

| 분류 | 이름 | 기준 |
|---|---|---|
| 기본: 이동 시설 | `엘리베이터`(16), `계단`(5) | 계단은 계단실 입구가 보이면 포함 |
| 기본: 화장실 | `화장실표시`(22), `화장실입구`(14) | 표시 = 픽토그램·TOILET 표지판, 입구 = 문 없는 스테인리스 틀·아코디언 문 |
| 기본: 안내·피난 | `비상구표시`(약 61), `안내판`(8) | 비상구표시는 천장 피난구유도등 + 벽 하단 통로유도등 모두 포함. 안내판 = 피난안내도·층 안내도 |
| 기본: 소방 | `소화전`(약 20), `소화기`(약 45) | 소화기는 바닥 소화기 + 벽 매립 "소화기" 함 모두 포함 |
| 기본: 기타 | `점자블록`(0), `정수기`(2), `자판기`(0) | 지금 사진엔 거의 없지만 다른 건물·층 확장 대비 |
| 구조 | `출입문`(135), `유리문`(26), `복도끝`(43), `기둥`(18) | 출입문 = 교실·연구실 문(남색·목재), 유리문 = 유리 출입문·현관문, 복도끝 = 복도 끝이나 T자 갈림길 |
| 자주 나오는 고정물 | `게시판`(51), `사물함`(37), `액자`(29), `CCTV`(27), `소파`(24), `노란바닥띠`(18), `미닫이문`(11), `셔터`(8) | 사물함은 4층, 소파·노란바닥띠는 5층, 미닫이문(회색 패널, 311·313호)·셔터는 3층에 몰려 있음 |

**목록에서 뺀 것**
- `창문`(91): 거의 모든 사진에 있고 대부분 복도 고창이라 위치 구분에 도움이 안 됨
- 호실표지판(124): 표지판 내용은 `rooms`/`spaces`가 담당
- 움직이는 물건: 배너, 휴지통·분리수거함, 테이블·의자, 잡지꽂이, 스탠딩책상, 이동식 디스플레이, 화분
- 사람마다 판단이 갈리는 것: 노란 비상용품함, 용도 모를 벽 매립 금속함·분전반, 벽부착 조명

**사진 조사에서 같이 나온 점**: 흐린 사진이 많음(4층 약 30장, 5층 약 9장), 같은 장소를 여러 번 찍은 사진이 많음(예: 4층 6/20/24/40), 사람이 찍힌 사진 있음(4층 6장).

> spaces와 landmarks 구분 예시
> - 문 위에 "화장실" 글자 → `spaces: ["화장실"]`
> - 화장실 픽토그램 표지판이 보임 → `landmarks: ["화장실표시"]`
> - 둘 다 있음 → 둘 다 기록

### 2-3. directions

모든 방향은 **대상(target)과 함께** 기록한다. `target`은 같은 사진의 `rooms`/`spaces`/`landmarks`에 있는 값 중 하나여야 한다.

| type | 의미 | 허용 값 |
|---|---|---|
| `SIGN_ARROW` | 표지판 화살표가 가리키는 방향 | `12시`~`11시`, `판단 불가` |
| `RELATIVE_POSITION` | 대상이 사진 속 어디에 있나 (카메라 기준) | `11시`, `12시`, `1시`, `판단 불가` |

- 기준: 12시 = 정면, 3시 = 오른쪽, 6시 = 뒤, 9시 = 왼쪽 (기존 navigation task와 동일)
- **SIGN_ARROW**: 화살표 모양 그대로 옮긴다. `↑`=12시, `→`=3시, `↓`=6시, `←`=9시, `↗`=2시, `↖`=10시, `↘`=4시, `↙`=8시.
  - 대각선은 실제로 1시 반 방향이라 애매하므로 채점에서 ±1시간을 허용한다 (6-3).
- **RELATIVE_POSITION**: 대상의 중심이 화면 **왼쪽 1/3 → 11시, 가운데 1/3 → 12시, 오른쪽 1/3 → 1시**.
  - 휴대폰 카메라 화각이 약 70°라 사진에 찍히는 범위는 10시~2시 정도. 사람마다 판단이 갈리지 않도록 3개 값만 쓴다.
  - 뒤쪽·옆쪽(3시~9시)은 사진에 보이지 않으므로 상대 위치에서는 쓰지 않는다.
  - 상대 위치는 **호실 번호와 길안내 핵심 랜드마크 7개**(엘리베이터, 계단, 화장실표시, 화장실입구, 비상구표시, 유리문, 복도끝)에만 기록한다. 출입문·게시판처럼 거의 모든 사진에 있는 것까지 적으면 정답 작성량이 너무 많아짐.
- 화살표가 있는데 대상이 무엇인지 모르면 `target: "UNKNOWN"`.

### 2-4. 정답 JSON 예시
```json
{
  "image_id": "4F_046",
  "ground_truth": {
    "rooms": ["410"],
    "floors": [],
    "spaces": ["강의실"],
    "landmarks": ["엘리베이터", "비상구표시"],
    "directions": [
      {"target": "엘리베이터", "type": "RELATIVE_POSITION", "value": "11시"},
      {"target": "비상구표시", "type": "SIGN_ARROW", "value": "3시"}
    ]
  },
  "uncertain": ["411"],
  "annotator": "작성자"
}
```

### 2-5. 정답 작성 절차
1. **파일럿**: 20장을 2명이 각자 작성 → 서로 다른 곳을 같이 보고 규칙 수정
2. 필드별 두 사람 일치율이 낮은 항목(특히 landmarks, directions)은 규칙을 더 구체화
3. 규칙 확정 후 176장을 나눠서 작성 (1인 약 35장), 각자 다른 사람 것 5장씩 교차 확인

## 3. 공통 프롬프트 v2

v1에서 바꾼 점: 예시 값을 데이터에 없는 값으로 교체, spaces/landmarks 구분, 제외 규칙, 방향 type별 허용 값, 반복 금지.

```
당신은 시각장애인의 실내 길안내를 돕기 위해 사진에서 이동 단서를 추출합니다.
사진은 대학 건물 안에서 사람 눈높이로 찍은 것입니다.

아래 5가지 항목을 JSON으로만 답하세요.

1. rooms: 문패나 표지판에 적힌 호실 번호.
   - "호"는 빼고 숫자, 하이픈, 알파벳만 보이는 그대로 씁니다. (형식 예: "999", "999-1")
   - 전화번호, 날짜, 포스터 속 숫자는 넣지 않습니다.

2. floors: 사진에 글자로 적힌 층 표시.
   - "n층"은 "nF"로, 지하는 "Bn"으로 씁니다.
   - 글자로 보이지 않으면 빈 배열로 둡니다.

3. spaces: 문패나 표지판에 글자로 적힌 공간 이름을 보이는 그대로 씁니다.

4. landmarks: 사진에 실제로 보이는 시설이나 물체. 아래 목록의 이름만 씁니다.
   엘리베이터, 계단, 화장실표시, 화장실입구, 비상구표시, 안내판, 소화전, 소화기, 점자블록, 정수기, 자판기, 출입문,
   유리문, 복도끝, 기둥, 게시판, 사물함, 액자, CCTV, 소파, 노란바닥띠, 미닫이문, 셔터

5. directions: 방향 정보. 각 항목은 target, type, value를 가집니다.
   - target: rooms, spaces, landmarks에 쓴 값 중 하나
   - 방향은 시계 방향으로 씁니다. 12시는 정면, 3시는 오른쪽, 6시는 뒤, 9시는 왼쪽입니다.
   - type이 SIGN_ARROW이면 표지판 화살표가 가리키는 방향:
     12시, 1시, 2시, … 11시 중 하나. 모르면 "판단 불가"
   - type이 RELATIVE_POSITION이면 대상이 사진의 어디에 있는지:
     왼쪽 1/3이면 11시, 가운데 1/3이면 12시, 오른쪽 1/3이면 1시, 모르면 "판단 불가"
   - RELATIVE_POSITION의 target은 rooms 값 또는 엘리베이터, 계단, 화장실표시, 화장실입구, 비상구표시, 유리문, 복도끝 중 하나

규칙:
- 사진에서 직접 확인한 것만 씁니다. 추측하지 않습니다.
- 확인할 수 없는 항목은 빈 배열 []로 둡니다.
- 같은 값을 반복해서 쓰지 않습니다.
- JSON 외의 설명은 쓰지 않습니다.

{"rooms": [], "floors": [], "spaces": [], "landmarks": [], "directions": []}
```

**프롬프트 예시 실험 (선택)**: lsh가 `same`/`noexample` 비교를 이미 준비해 두었으므로, v2에서도 "형식 예시 있음/없음" 두 버전을 돌려 예시 베끼기 정도를 확인할 수 있다.

## 4. 출력 형식 강제

- **Ollama**: `format`에 JSON Schema를 넣어 구조와 허용 값(enum)을 강제한다.
  ```json
  {
    "type": "object",
    "properties": {
      "rooms":     {"type": "array", "items": {"type": "string"}},
      "floors":    {"type": "array", "items": {"type": "string"}},
      "spaces":    {"type": "array", "items": {"type": "string"}},
      "landmarks": {"type": "array", "items": {"type": "string", "enum": ["엘리베이터","계단","화장실표시","화장실입구","비상구표시","안내판","소화전","소화기","점자블록","정수기","자판기","출입문","유리문","복도끝","기둥","게시판","사물함","액자","CCTV","소파","노란바닥띠","미닫이문","셔터"]}},
      "directions": {"type": "array", "items": {
        "type": "object",
        "properties": {
          "target": {"type": "string"},
          "type":   {"type": "string", "enum": ["SIGN_ARROW", "RELATIVE_POSITION"]},
          "value":  {"type": "string", "enum": ["12시","1시","2시","3시","4시","5시","6시","7시","8시","9시","10시","11시","판단 불가"]}
        },
        "required": ["target", "type", "value"]
      }}
    },
    "required": ["rooms", "floors", "spaces", "landmarks", "directions"]
  }
  ```
- **HF transformers** (lsh 방식): schema 강제가 없으므로 답 시작을 `{"rooms": [` 로 미리 채운다(prefill). 조건 차이로 기록.
- 채점 시 추가 검사: type별 허용 값 위반(예: RELATIVE_POSITION에 3시), target이 다른 필드에 없는 경우 → **형식 위반**으로 집계.

## 5. 실행 환경

| 항목 | 기준 | 비고 |
|---|---|---|
| 이미지 | 긴 변 1024px, JPEG 85 | 기존 signs와 동일 |
| temperature | 0 | |
| seed | 42 | Ollama `options.seed` |
| top_p / top_k | 기본값 | temperature 0이면 결과에 영향 없음 |
| 최대 출력 토큰 | 512 | Ollama `num_predict`, HF `max_new_tokens`. **반복 루프 방지에 필수** |
| timeout | 60초 | GPU 기준. CPU는 30초 안팎이 걸려 비교 불가 → **GPU 실행만 결과로 인정** |
| 추론 | Ollama 0.24.0 (`11435`, GPU) | 지금 꺼져 있음. 누가 띄울지 합의 필요 |
| 양자화 | Ollama 기본(q4_K_M) | HF는 fp16 → **다른 조건이므로 별도 표로 비교** |
| warm-up | 1회 | 첫 요청의 모델 로딩 시간 제외 |
| 반복 | 이미지당 1회 | temperature 0이라 같은 답이 나와야 함. 10장은 2회 돌려 재현성 확인 |


### 5-1. 원본 사진 상태 (10/17 서버 확인)
| 층 | 원본 해상도 | 파일 크기(중앙값) | 기기 | EXIF 회전 |
|---|---|---|---|---|
| 3층 | 1058×1411 (세로 79, 가로 22) | 283KB | 정보 없음 (EXIF 제거됨) | 없음 |
| 4층 | 4000×3000 (77장), 1058×1411 (4장) | 3.1MB | Galaxy S22 | 모두 1 (정상) |
| 5층 | 5712×4284 (43장), 4032×3024 (1장) | 3.1MB | iPhone 17 | 모두 1 (정상) |

- 회전 문제 없음 → 지금 코드로도 사진이 똑바로 들어감
- **3층은 이미 압축된 사진** (메신저로 전송되며 줄어든 것으로 추정). 1024로 줄여도 손실이 거의 없지만, 해상도를 올려도 나아지지 않음
- 4·5층은 1024로 줄이면 픽셀이 1/15~1/23로 줄어듦 → 해상도 실험은 **4·5층으로** 해야 효과가 보임
- 층별 비교를 하면 해상도 차이가 섞임. 3층 원본을 가진 사람이 있으면 다시 받기

## 6. 평가 방법

### 6-1. 값 정규화 (채점 전)
- 공통: 앞뒤 공백 제거, 내부 공백 제거, 영문 대문자로
- rooms: "호" 제거
- floors: `3층`→`3F`
- spaces: 정답 값이 모델 값에 포함되거나 그 반대면 일치 (`"강의실1"` ↔ `"강의실 1"`). 한 글자 값은 정확히 같아야 일치
- 동의어 표: 이번 실험에서는 쓰지 않음 (10/17 결정). 보이는 글자 그대로 비교
- `uncertain`에 있는 값은 정답에서도 모델 답에서도 뺀다

### 6-2. 필드별 점수 (rooms, floors, spaces, landmarks)
- 사진마다 정답 집합과 모델 집합을 비교해 TP / FP / FN을 센다
- **micro 평균**(전체 TP·FP·FN 합산 후 계산)을 대표 점수로, 사진별 평균(macro)은 참고용
- 정답이 빈 사진은 F1을 계산하지 않고 6-4의 지어내기 비율로 따로 본다

### 6-3. directions
target이 일치한 항목만 비교한다.

| 지표 | 계산 |
|---|---|
| target 재현율 | 정답 direction 중 모델이 같은 target을 낸 비율 |
| type 정확도 | target 일치 항목 중 type까지 같은 비율 |
| value 정확도 | target·type 일치 항목 중 value까지 같은 비율 |
| ±1시간 허용 정확도 | value가 1시간 차이(예: 1시 ↔ 2시, 12시 ↔ 11시)면 정답으로 인정. 대각선 화살표 때문에 **대표 점수와 함께 반드시 보고** |

### 6-4. 오류 유형 분류
모델이 낸 값과 정답 값을 하나씩 짝지어 분류한다.

| 유형 | 판정 |
|---|---|
| 정확 | 정규화 후 일치 |
| 오인식 | 같은 필드의 정답 값과 **한두 글자만 다름** (rooms: 편집 거리 1, 예 `410`→`411`) |
| 누락 | 정답에 있는데 모델 답에 대응되는 값이 없음 |
| Hallucination | 모델 답에 있는데 대응되는 정답 값이 없음 (오인식 제외) |

추가 지표: **빈 사진 지어내기 비율** = 정답 필드가 비어 있는 사진 중 모델이 그 필드에 값을 낸 비율.
signs 실험의 gemma3 `410` 문제를 직접 잡는 숫자.

### 6-5. 실행 성능
평균·중앙값 응답 시간, timeout 비율, JSON 파싱 성공률, 형식 위반률(4절)

### 6-6. 결과 표 형식
| 모델 | rooms F1 | floors F1 | spaces F1 | landmarks F1 | dir value 정확도 | 지어내기 비율 | 파싱 성공률 | 응답 시간(중앙값) |
|---|---|---|---|---|---|---|---|---|

층별(3F/4F/5F) 표도 함께 낸다.
